# 0. Стенд и его границы

## 0.1. Как он собран — воспроизводимо

Изолированная копия `/home/user/fabric-server-26.2` в скретчпаде, **порт 25671**, собственный мир
(`level-type=flat`, `level-name=gworld`, `difficulty=normal`), jar 0.0.20. Всё измерительное железо
живёт **вне репозитория**, в `<scratchpad>/gd/`; исходники мода при измерениях не менялись.

Порядок сборки стенда — ровно этот, и порядок важен:

```
setup.sh          копия сервера, server.properties (порт 25671, flat, gworld, normal)
start.sh          запуск с -XX:+EnableDynamicAgentLoading, stdin из fifo in.fifo
attach.sh         подключение GuardAgent через Attach API
say.sh  "<cmd>"   консольная команда серверу через fifo
ctl.sh  "<cmd>"   команда измерительному агенту через ctl.txt
```

**Первое, обо что я споткнулся и на что уйдёт полчаса у следующего:** без игрока загружены только
чанки спавна, и `/setblock` за их пределами отвечает `That position is not loaded`, а
`Block#setPlacedBy` тогда возвращает `null` вместо здания. Лечится одной строкой **до** всякой
стройки:

```
forceload add -112 -112 112 112      # 225 чанков, максимум за раз — 256
```

Дальше:

```
say  setblock 0 -60 0 minecolonies:blockhuttownhall
ctl  colony 0 -60 0                  # IColonyManager#createColony с FakePlayer
ctl  place  0 -60 0 5                # setPlacedBy + setBuildingLevel(5) + isBuilt = true
```

**Второе.** Колония без подписчика остаётся `INACTIVE` (`Colony.updateState`), а в этом состоянии не
работает `worldTickSlow` — то есть **не рождаются граждане** и не тикают здания. Эта ветка чинила
утечку fake-игроков в подписчики (`ColonyPackageManager.addCloseSubscriber` теперь их отбрасывает),
поэтому приём из `WORKER-AUDIT.md` больше не срабатывает сам. Агент вставляет fake-игрока
**напрямую в поле** `closeSubscribers` (команда `activate`) — колония переходит в `ACTIVE`, граждане
рождаются, здания тикают. Мод при этом не меняется.

**Третье — то, что съело у меня больше всего времени.** **Одна башня стражи вмещает ровно одного
стражника.** `BuildingModules` даёт башне пять модулей найма (knight, ranger, druid, marksman,
huscarl), у каждого предел `(b) -> 1`, а `GuardBuildingModule.isFull()` переопределён на
`building.getAllAssignedCitizen().size() >= getModuleMax()` — то есть считает **всех** назначенных в
здание, а не в модуль. Шесть стражников = шесть башен. Автонайм всегда добирается до модуля рыцаря
первым, поэтому лучники получаются только через `unhire` + `hire <x y z> 1 ranger`.

Итоговый стенд: ратуша (0,-60,0), **шесть башен стражи** — три западные (x=-30, z=-20/0/20) под
рыцарей, три восточные (x=+30) под лучников, двенадцать жилых хижин, до 25 граждан.
Свободный режим (`/mc colony freemode 1 on`) выдаёт стражникам незеритовое оружие и броню — иначе
половина времени уходит в `NEEDS_ITEM` (см. `WORKER-AUDIT.md` §2.3).

## 0.2. Инструменты

Три java-агента, все read-only по отношению к моду, все вне репозитория:

* **`GuardAgent`** — переработан из `WorkAgent` предыдущего круга. Семплер состояний: каждые 50 мс
  обходит граждан и пишет `(профессия, состояние, сдвинулся ли)`; плюс счётчик переходов; плюс
  **счётчик новых объектов `PathResult`** у навигатора каждого стражника (нижняя оценка числа
  запросов к поиску пути, отдельно по профессии). Плюс постройка колонии, найм/увольнение,
  правка настроек здания, урон/лечение, дамп стражников.
* **`Probe`** — точечные вопросы: подсчёт урона от топоров, выдача исследовательских эффектов,
  чтение конфига, ростер стражи.
* **`Probe2`** — read-only наблюдатель **таблицы угроз**: раз в 200 мс, **на серверном потоке**,
  читает приватные поля `ThreatTable` (список, индекс текущей цели, угроза, `lastSeen`) и пишет CSV.
  `ThreatTable#getTarget()` он **не** зовёт: этот метод мутирует список (`removeCurrentTarget`).

Agent-классы разные, поэтому второй и третий агенты подключаются к живому серверу **без
перезапуска** — это экономит по полторы минуты на каждый новый вопрос.

Нагрузка на поиск пути снята штатным инструментом дерева — `PathfindingStats` (то, что печатает
`/mc pathstats`), — через агент, чтобы числа попадали в лог машинно.

# 2. Три гипотезы, которые измерение опровергло

Записываю их первыми, потому что они звучат правдоподобно, и следующий круг иначе потратит на них
время заново.

## 2.1. «Патрулирующий стражник постоянно перезапрашивает путь» — **неверно [ИЗМЕРЕНО]**

Задание прямо называет это «правдоподобным налогом, который никто не посчитал». Посчитал: четыре
стражника в патруле дают **0.29 задания в секунду на всех**, пул занят **0.1 %**. Причина в коде:
`EntityNavigationUtils.walkToPos` перезапрашивает путь только если `nav.isDone()` **или** текущее
задание построено не к той точке; `decide()` при этом зовётся раз в 100 тиков (5 с). То есть один
патрульный отрезок — это одно задание `PathJobMoveToLocation` плюс, примерно в половине случаев,
одно `PathJobRandomPos` на выбор следующей точки (`AbstractBuildingGuards.getNextPatrolTarget`).

**Оговорка, без которой число врёт:** мир плоский, все 125 заданий дошли до цели с первого раза.
Ветка «цель недостижима» существует и стоит дорого — она измерена в §3.2.

## 2.2. «Рыцарь перезапрашивает путь на каждый удар» — **неверно [ИЗМЕРЕНО]**

`MeleeCombatAI.doAttack` (`:199-202`) делает `if (user.distanceTo(target) > 1) moveInAttackPosition(target)`
на **каждом** ударе, а `MAX_DISTANCE_FOR_ATTACK = 2`, то есть условие в ближнем бою почти всегда
истинно. Выглядит как один поиск пути на взмах.

На деле — нет. `EntityNavigationUtils.walkToPos` выходит раньше:
`BlockPosUtil.dist(entity.blockPosition(), desiredPosition) <= REACHED_DIST (1.5)` → `nav.stop()`,
`return true`, **без задания**. Рыцарь в ближнем бою стоит на соседнем блоке, расстояние в блочных
координатах 1.0, и заданий не порождается. Измерено: три рыцаря в бою — **0.13 нового `PathResult`
в секунду на всех**, `PathJobMoveToLocation` по 60 узлов и 0.30 мс.

## 2.3. «Лучник на посту жжёт пул своим топтанием» — **неверно [ИЗМЕРЕНО]**

`EntityAIRange.guardMovement()` (`:66-86`) каждые 5 с, если навигация свободна, ставит новое задание
`PathJobWalkRandomEdge`. Лучник действительно топчется 47 % времени против 9 % у рыцаря и даёт
в 11 раз больше заданий. Но само задание — **самое дешёвое в таблице**: `isAtDestination` объявляет
целью любой проходимый узел с шансом 1/10, поэтому поиск заканчивается на **10-15 узлах за
0.19-0.37 мс**. Три лучника за 422 с — 121 задание и **33 мс суммарно**. Трогать нечего.

# 3. Находки

Отсортировано по тому, что увидит игрок.

## 3.1. Рыцарь не видит врага выше или ниже себя на три блока **[ИЗМЕРЕНО]**

**Что происходит.** `TargetAI.getYSearchRange()` возвращает `Y_VISION = 3`, и это половина высоты
коробки, в которой стражник вообще ищет цели (`getSearchArea`, `:241-243`). По горизонтали коробка
32-48 блоков, по вертикали — **±3**. `RangeCombatAI` переопределяет это на `Y_VISION + 25 = 28`, но
**только для лучника и только на задаче `GUARD`**. Рыцарю не переопределяет никто.

**Измерено, обе стороны одним опытом.** У каждой из шести башен — обелиск из обсидиана в четырёх
блоках, на нём зомби, на шесть блоков выше стражника, прямая видимость, 250 с:

| | захватов цели | доля времени в `ATTACKING` |
|---|---|---|
| три рыцаря | **0** | **0.0 %** |
| три лучника | 3 | 9.3 % |

Ноль. Рыцари 95.9 % времени простояли в `NO_TARGET` (движение 3 %), поспали и разбудили друг друга,
пока над ними в четырёх метрах сидели зомби.

**Что видит игрок.** «Мои рыцари не замечают мобов на стене / на крыше / на холме». Рыцарь у
подножия собственной двухэтажной башни не видит моба на её крыше.

**Апстрим.** `Y_VISION = 3` и обе реализации `getYSearchRange` байт-в-байт совпадают с 1.21.1.
Это не регрессия порта.

**Правка.** Сделана: **конфиг `guardverticalvision`, по умолчанию 3 — то есть сегодняшнее
поведение**. Поднятие меняет то, **какие** цели стражник выбирает, то есть баланс, поэтому по
умолчанию не меняется ничего. `TargetAI.getYSearchRange()` читает конфиг; `RangeCombatAI` берёт
`Math.max(super.getYSearchRange(), Y_VISION + 25)`, чтобы общий конфиг не мог **уменьшить** обзор
лучника. **~6 строк кода + одна запись конфига.**

**Цена, о которой надо сказать честно.** Коробка поиска — `getEntitiesOfClass` раз в 4 с на
стражника, её объём линеен по этому числу: с 3 до 28 — это **примерно ×9 по объёму**. И, как
показано в §3.2, поднятие обзора **делает частым** тот случай, который до этого был редким.
Рекомендация владельцу: если поднимать, то до 8-12 (этаж-два), а не до 28.

## 3.2. Стражник с недостижимой целью мечется между `NO_TARGET` и `ATTACKING` **[ИЗМЕРЕНО]**

**Как нашлось.** Не поиском, а как побочный эффект включения §3.1: подняв `guardverticalvision`
до 28, я получил рыцарей, которые цель **видят**, но взобраться на обелиск не могут.

**Что происходит.** `TargetAI.searchNearbyTarget()` считает поиск успешным (`foundTarget = true`,
то есть переход в `ATTACKING`) для любой сущности, прошедшей `isEntityValidTarget` и проверку
прямой видимости — **не спрашивая таблицу угроз, отдаст ли она эту цель**. А цель, от которой
стражник уже отказался, помечена `markInvalidTarget()` угрозой `-1`, и `ThreatTable.getTarget()`
такую запись возвращать отказывается (`if (current.getThreat() < 0) return null`). Итог: машина
состояний уходит в `ATTACKING`, `checkForTarget()` на следующем тике возвращает её в `NO_TARGET`, и
так каждое сканирование, пока враг стоит на месте.

**Измерено, до и после, один и тот же опыт (три рыцаря, три недостижимых зомби, 250 с):**

| | до | после |
|---|---|---|
| круги `NO_TARGET → ATTACKING → NO_TARGET` | **86** | **11** |
| доля времени в `ATTACKING` | 10.8 % | 8.5 % |
| заданий поиска пути | 112 | 105 |
| из них упёрлись в предел узлов | 32 (29 %) | 28 (27 %) |
| дубликатов поиска | 12 | 9 |
| `PathJobMoveToLocation` дошли | 31 % | 34 % |

**Правка.** Сделана, одна строка по существу в `TargetAI.searchNearbyTarget`:

```java
foundTarget |= user.getThreatTable().getThreatFor(entity) >= 0;
```

вместо безусловного `foundTarget = true`. Решения не меняются: угрозу `-1` ставит собственная логика
отказа стражника, и снимается она ровно как раньше — запись стареет из таблицы через
`MAX_TRACKING_TICKS`, либо враг бьёт стражника и `addThreat` поднимает угрозу выше нуля.

**Чего эта правка НЕ делает — и это важно.** Задания поиска пути почти не изменились
(112 → 105, упёршихся в предел 32 → 28). Они тратятся на **те заходы в бой, которые всё-таки
случились**, а это законная работа: стражник обязан один раз попробовать дойти. Правка убирает
дрожание машины состояний после того, как стражник **уже решил** сдаться, а не первую попытку.
Кто ждёт от неё выигрыша в мспт — не дождётся; кто смотрит на стражника — увидит, что тот
перестал дёргаться.

**Проверка на регресс.** Со стоковым конфигом и 18 обычными достижимыми зомби: рыцари 8.5 %
`ATTACKING` (10 захватов), лучники 21.4 %, **114 заданий поиска, 100 % дошли, 0 упёршихся в предел,
0 дубликатов**. Обычный бой не сломан.

**Апстрим.** `searchNearbyTarget` в этом месте байт-в-байт совпадает с 1.21.1 — правка апстримовская.

## 3.3. Стражник спит на посту среди бела дня **[ИЗМЕРЕНО]**

**Что происходит.** `AbstractEntityAIGuard.shouldSleep()` (`:272`) — переход из `NO_TARGET`
с тикрейтом `SHOULD_SLEEP_INTERVAL = 200` тиков (10 с). **Проверки времени суток в нём нет.**
Шанс — `worker.getRandom().nextInt((int)(Adaptability * 0.5) + 20) == 1`, то есть 1/20 у новичка,
каждые 10 с. Сон длится 2500-3000 тиков (125-150 с). Разбудить может только другой стражник:
`MeleeCombatAI.skipSearch` / `RangeCombatAI.skipSearch` замечают спящего коллегу в 16-блочной
коробке, ставят `GUARD_WAKE`, тот подходит и **бьёт его на 1 единицу урона** (`wakeUpGuard`, `:259`).

**Измерено, четыре окна, всё при `time set day`:**

| окно | `GUARD_SLEEP` рыцаря | `GUARD_SLEEP` лучника | `GUARD_WAKE` |
|---|---|---|---|
| патруль, 422 с | 11.1 % | 4.9 % | 2.6 % / 3.6 % |
| пост, 422 с | 2.6 % | 12.7 % | 2.9 % / 3.3 % |
| бой, 182 с | — | 7.6 % | 1.5 % / 5.0 % |
| обзор, 250 с | 2.7 % | 16.8 % | 1.3 % / 0 % |

То есть **от 2.6 % до 16.8 % рабочего дня стражник спит**, плюс ещё 1-5 % кто-то тратит на дорогу
до спящего. Ни в одном окне не была ночь.

**Что видит игрок.** Гарнизон дремлет в полдень; рейд начинается — часть стражи просыпается не
сразу. Сон **прерывается** боем корректно: в окне боя зафиксирован переход
`GUARD_SLEEP → ATTACKING` напрямую.

**Апстрим.** Файл отличается от 1.21.1 только переименованиями ванильных API. Механика задумана —
её ослабляет исследование `SLEEP_LESS`. Но комментарий в коде («Chance is 1 in (10 + level/2) =
1 in Level1:5») **не соответствует коду** (`+ 20`, а не `+ 10`), так что настоящие числа никто,
похоже, не пересчитывал.

**Правка.** Сделана: **конфиг `guardsfallasleep`, по умолчанию `true` — сегодняшнее поведение**.
`false` выключает механику целиком. **4 строки + запись конфига.** Проверено на стенде: с `false`
за 250 с — **ноль семплов `GUARD_SLEEP` и `GUARD_WAKE`**.

## 3.4. Раненый стражник лечится сам, 75 секунд, и лекарь тут ни при чём **[ИЗМЕРЕНО]**

Полный цикл снят на живом сервере. Условия: исследование `RETREAT` выдано агентом (без него ветка
мертва, см. §3.5), настройка `RETREAT` у башни включена по умолчанию, рыцарям в бою сброшено
здоровье до 7 из 72-73 (меньше 20 %).

**Что произошло, по переходам и по времени:**

```
NO_TARGET → GUARD_FLEE   ×2      5.0 с на стражника   (бег к своей башне, движение 81 %)
GUARD_FLEE → GUARD_REGEN ×2     75.0 с на стражника   (стоит у башни, движение 0 %)
GUARD_REGEN → START_WORKING ×2   4.9 с
START_WORKING → DECIDE → NO_TARGET               (вернулся на пост)
```

Здоровье: 7 → 41 за 60 с → 63 за 120 с, то есть **примерно 0.4-0.5 ед/с** (эффект
`REGENERATION`, который `regen()` подновляет сам). Выход из `GUARD_REGEN` — при 75 % от максимума,
ровно как написано в `regen()` (`:388`). Оба рыцаря **вернулись на свои посты**.

**Ответ на вопрос задания «взаимодействие с лекарем»: его нет.** Ни одного обращения к больнице.
`CitizenAI.calculateNextState` (`:137-152`) для стражника проверяет только `isSick()` (болезнь), а
не `isHurt()` (раны), и лечение стражника целиком сводится к трём собственным источникам:
эффект `REGENERATION` в `GUARD_REGEN`, +0.5 HP каждые 30 тиков во сне (`sleepParticles`, `:316`) и
еда. **[ПО КОДУ]** для механизма, **[ИЗМЕРЕНО]** для результата.

**Цена, которую стоит знать владельцу:** раненый стражник выключен из обороны на **~75 секунд**, и
на это время его пост пуст.

## 3.5. Без исследования стражник дерётся насмерть **[ИЗМЕРЕНО]**

`shouldFlee()` (`:366`) возвращает `true` только если
`getResearchEffects().getEffectStrength(RETREAT) > 0`. Исследование — `combat/regeneration`
(башня стражи 2 уровня, 1 изумруд), название в интерфейсе «Guards Flee Under 20% HP». То же условие
внутри `regen()`: `shallRetrieveOnLowHealth()` — это настройка здания, но сам вход в `GUARD_FLEE`
заперт исследованием.

**Измерено.** Первый боевой заход я поставил **до** выдачи исследования: девять зомби по 200 HP
против шести стражников. Все **шесть погибли**, ни одного перехода в `GUARD_FLEE` за 187 с.
Во втором заходе, с выданным исследованием, побег сработал с первого раза (§3.4).

Это дизайн, а не поломка, и он воспроизводится на 1.21.1. В отчёте — потому что «стражники мрут
пачками на свежей колонии» имеет ровно одну причину и ровно одно лекарство ценой в изумруд.

## 3.6. Мелочи, найденные чтением и не тронутые **[ПО КОДУ]**

* **`AbstractEntityAIGuard.target` — мёртвое поле.** Объявлено (`:95`), объявлено ещё раз в
  `AbstractEntityAIFight` (`:57`), и **не присваивается нигде**. Настоящая цель живёт в
  `TargetAI.target` и в таблице угроз. Читает мёртвое поле `shouldSleep()`: проверка
  `target != null` всегда ложна. Практического вреда нет — `shouldSleep` работает только в
  `NO_TARGET`, где цели и так нет, а недавнюю атаку ловит `worker.getLastHurtByMob()`. Но это
  ловушка для следующего, кто будет править сон. Байт-в-байт как в 1.21.1.
* **`shouldFlee` сравнивает квадрат расстояния с 20.**
  `worker.distanceToSqr(Vec3.atCenterOf(building.getID())) > 20` — это «дальше 4.47 блока», хотя по
  соседним константам (`MAX_GUARD_DERIVATION = 10`, `MAX_FOLLOW_DERIVATION = 30`) явно имелись в
  виду 20 блоков, то есть 400. Апстрим. Правка — это изменение решения (когда стражник считает, что
  он «достаточно далеко от дома, чтобы бежать»), поэтому оставлено владельцу.
* **`RangeCombatAI.getAttackDistance()` обходит собственный потолок.**
  `Math.min(attackDist, MAX_DISTANCE_FOR_RANGED_ATTACK = 24)` применяется **до** прибавки за высоту
  `attackDist += user.getY() - target.getY()`. Лучник на башне в 20 блоках над целью получает
  дальность 44, а не 24. Апстрим, баланс.
* **`AttackMoveAI.move()` отпускает недостижимую цель не сразу.** Угроза свежей цели — 10 плюс до 7
  за близость, то есть ~16; каждые шесть неудачных попыток пути снимают единицу, отказ наступает
  ниже 5. Это до ~66 попыток. На стенде до этого не доходило (см. §3.2: 29 % заданий упирались в
  предел узлов, но цели было три, а рыцаря три). На настоящем рельефе это тот самый шов, за который
  стоит потянуть следующему кругу.

# 4. Отдельно: урон стражника с топором

## 4.1. Что даёт каждая формула, в числах **[ИЗМЕРЕНО]**

`WORKER-AUDIT.md` §2.9 нашёл единственное расхождение порта с апстримом во всём дереве работников и
попросил не переворачивать его вслепую. Числа сняты на живом сервере (агент `Probe`, команда
`axecalc`: для каждого ванильного топора читается `ItemAttributeModifiers#compute(ATTACK_DAMAGE, 0,
MAINHAND)` — слагаемое порта — и `ItemStack#getDamageValue()` вместе с `getMaxDamage()` — слагаемое
апстрима, потому что NeoForge-расширение `Item#getDamage(stack)` это ровно `getDamageValue()`).

`BASE_PHYSICAL_DAMAGE = 3`, `guardDamageMultiplier = 1.0` (значение по умолчанию, проверено на
сервере). Урон за удар до крита и исследований:

| топор | слагаемое порта | **порт** | **апстрим 1.21.1** (новый … изношенный) |
|---|---|---|---|
| деревянный | 6.0 | **9** | 3 … 62 |
| каменный | 8.0 | **11** | 3 … 134 |
| медный | 8.0 | **11** | 3 … 193 |
| золотой | 6.0 | **9** | 3 … 35 |
| железный | 8.0 | **11** | 3 … 253 |
| алмазный | 8.0 | **11** | 3 … 1564 |
| незеритовый | 9.0 | **12** | 3 … 2034 |

Для масштаба, на том же стенде: **рыцарь с незеритовым мечом — 10.0** (ветка `ItemTags.SWORDS`
читает атрибут сущности: 3.0 базовых у гражданина + 7.0 от меча).

Механизм роста подтверждён прямым наблюдением, а не рассуждением: у рыцаря #3 после боя
`stack.getDamageValue()` показал **5** — то есть слагаемое апстрима действительно растёт на единицу
за каждый удар (`CitizenItemUtils.damageItemInHand(..., 1)` в конце `doAttack`).

## 4.2. Что из этого следует и что я рекомендую

Апстримовский хускарл **начинает слабее безоружного гражданина** (3 против 10 у рыцаря с мечом) и
**заканчивает способным убить что угодно в игре с одного удара** (2034), и всё это — функция от
того, насколько поцарапан его топор. Это не выбор баланса, это чтение не того поля: `Item#getDamage`
в NeoForge возвращает израсходованную прочность.

**Рекомендация: оставить как в порте.** Это исправление, а не ребаланс: 9-12 против 10 у рыцаря —
ровно тот порядок, в котором ветка меча и задумана. **Флип не сделан.**

Что сделано: расхождение **перестало быть немаркированным**. В `MeleeCombatAI.getAttackDamage()`
поставлен `PORT-NOTE` с этой таблицей и с объяснением, откуда взялась апстримовская формула
(**~18 строк комментария, ноль изменений поведения**). Если владелец решит вернуть апстрим — это
три строки, и он теперь знает, что именно вернёт.

Отдельно стоит знать: ветка топора работает **только у хускарла** (`MeleeCombatAI.getWeaponType()`
отдаёт топор ему и меч всем прочим рыцарям), а хускарл заперт за исследованием. То есть цена
вопроса — одна профессия поздней игры.

## 9.5. Опыты, которые уже поставлены и их условия

| опыт | как ставится |
|---|---|
| обычный бой | `say summon minecraft:zombie -42 -60 <z> {PersistenceRequired:true}` ×3 у каждой башни, `time set midnight` (иначе зомби горят) |
| побег и лечение | сначала `p research minecolonies:effects/retreatunlock 1`, затем в бою `p hp <id> 7` |
| недостижимая цель | `fill -26 -60 z -26 -55 z obsidian` + зомби на вершине; **работает только при поднятом `guardverticalvision`**, иначе рыцарь его не видит (§3.1) |
| вертикальный обзор | одинаковые обелиски у башен рыцарей (x=-26) и лучников (x=+26), сравнивать доли `ATTACKING` |
| урон топоров | `p axecalc` — читает данные предметов, стражник для этого не нужен |
| таблица угроз | `p2 watch <id>` -> `threat-<id>.csv`, колонки `state, entries, idx, threat, lastSeenAgo, entity, dist` |

## 9.6. Ловушки, стоившие времени

* **`forceload` до всего остального**, иначе `place` молча даёт `null`.
* **Ров вокруг цели не делает её недостижимой** — рыцарь всё равно дошёл (в трассе расстояние упало
  до 0.12). Обелиск надёжнее, но требует поднятого вертикального обзора.
* **Зомби с раздутым здоровьем убивают весь гарнизон.** Девять зомби по 200 HP против шести
  стражников — все шесть погибли за три минуты. Для измерения боя нужны обычные.
* **Смена конфига требует перезапуска** (`setcfg.sh <vision> <sleep>`): TOML читается при загрузке.
* **Свободный режим слетает при перезапуске сервера не всегда** — включать заново перед каждым окном.
