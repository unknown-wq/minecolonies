# 0. Стенд: как он собран и как его пересобрать

## 0.1. Главное отличие от прошлого круга

Прошлый стенд ставил хижину командой `/setblock` и вызывал `Block#setPlacedBy`. Здание при этом
регистрируется, но у него нет ни чертежа, ни углов, ни стоек, ни бочек, ни печей, ни шахты. Здесь
хижина ставится **тем же путём, каким её ставит строительный инструмент**, и сразу после этого чертёж
**вставляется в мир**.

Порядок обязателен, и он не очевиден:

1. `Level#setBlockAndUpdate(pos, anchorState)` — якорь.
2. `AbstractBlockHut#onBlockPlacedByBuildTool(level, pos, state, player, stack, RotationMirror.NONE, pack, path)`
   (`api/blocks/AbstractBlockHut.java:113`). Он кладёт на TileEntity `packName` + `blueprintPath` +
   поворот и зовёт `setPlacedBy` — **здание появляется в колонии здесь**.
3. Только теперь — вставка чертежа. `CreativeBuildingStructureHandler` в конструкторе делает
   `setupBuilding()` (`api/util/CreativeBuildingStructureHandler.java:88`), то есть **ищет здание в момент
   создания хендлера**. Если здания ещё нет, `triggerSuccess` потом не вызовет
   `building.registerBlockPosition`, и стойки/бочки/печи не будут привязаны к зданию — блоки в мире
   будут, а работник их не увидит. Это ровно та ошибка, которую я сделал на первой попытке с ратушей:
   `containers=1`, то есть ни одной стойки.
4. `building.setBuildingLevel(N)` + `onUpgradeComplete(blueprint, N)` — углы, захват чанков, `isBuilt`.

**Отдельная находка по дороге** (§2.8): штатный вход `CreativeBuildingStructureHandler.loadAndPlaceStructureWithRotation(Level, Future<Blueprint>, …)`
не ставит **ничего**. Пришлось разрешать чертёж синхронно и собирать
`CreativeBuildingStructureHandler(Level, BlockPos, Blueprint, RotationMirror, boolean)` →
`StructurePlacer` → `Manager.addToQueue(new PlaceStructureOperation(placer, player))` руками.

## 0.5. Колония должна быть ACTIVE, иначе половина измерения — артефакт

`Colony.updateState` (`core/colony/Colony.java:472-480`) даёт `ACTIVE` только когда есть **близкий
подписчик-игрок**. Без него не тикают `tickWorkManager` (заказов на строительство не существует) и
`tickRequests` (заявки не переспрашиваются). Прошлый круг это записал; здесь это снято.

Обход: `ColonyPackageManager.closeSubscribers` пополняется fabric-овым `FakePlayer`, поставленным внутрь
захваченных чанков. Его пакетный слушатель (`FakePlayerPacketListener$FakeConnection`) молча выбрасывает
пакеты, так что `updateColonyViews` безвреден. **Измерено:** до подписки строитель 100 % в `INIT` и
заказов ноль; через несколько секунд после — курьер поехал в `PICKUP`, а после выдачи заказа строитель
ушёл в `BUILDING_STEP`.

# 2. Находки

## 2.1. Печные профессии сбрасывают инвентарь **после каждого действия** — 23 % рабочего дня плавильщика **[ИЗМЕРЕНО + ПО КОДУ]**

**Что происходит.** `AbstractEntityAIUsesFurnace.getActionsDoneUntilDumping()`
(`core/entity/ai/workers/AbstractEntityAIUsesFurnace.java:378`) возвращает **1**, с комментарием
«dump inventory after every action». Общий по моду порог — `ACTIONS_UNTIL_DUMP = 32`
(`api/util/constant/CitizenConstants.java:177`). То есть печник ходит к сундуку **в 32 раза чаще**
всех остальных.

Каждый такой поход стоит не мгновение: `new AITarget(INVENTORY_FULL, this::dumpInventory, 20)`
(`AbstractEntityAIBasic.java:233`), а `dumpOneMoreSlot()` (`:1270`) кладёт в сундук **один занятый слот
за вызов**. Тикрейт 20 — это один слот в секунду. Это тот самый §2.8 прошлого круга, но там он был
подтверждён косвенно (4.1 с у лесоруба); здесь он снят на работнике, который упирается в него постоянно.

**Измерено.** Плавильщик за 2743 с: **623 захода в `INVENTORY_FULL`, 623.3 с суммарно — 22.7 % рабочего
дня, при 5 % движения**. Средний заход ≈ 1.0 с, то есть ровно один слот. Цикл выглядит так:
`START_WORKING` ~3 с → `INVENTORY_FULL` 1 с → `IDLE` 0.25 с → снова.

**Побочный эффект, который тоже измерен.** Курьер на этом стенде провёл **82 % дня** в `PICKUP`+`DUMPING`
(1504 + 747 с), обслуживая в основном эти же 623 микро-сброса: `dumpInventory` при непустом
`dumpedItems` создаёт `createPickupRequest`. То есть цена решения «сбрасывать после каждого действия»
платится дважды — временем печника и временем курьера.

**Что видит игрок.** Плавильщик и повар бо́льшую часть времени топчутся между печью и сундуком.
Курьер вечно занят и не успевает к остальным.

**Апстрим или порт.** **Апстрим.** `diff -u` с 1.21.1 по `AbstractEntityAIUsesFurnace.java` — 9
изменённых строк, все механические: импорты, `isLit()` → `litTimeRemaining > 0`,
`furnace.serverTick(...)` → `FurnaceBlockEntity.serverTick((ServerLevel) …)`. `getActionsDoneUntilDumping`
байт-в-байт.

**Правка.** Две независимые, обе крошечные:
* `return 1;` → `return Math.max(1, building.getModule(FURNACE).getFurnaces().size());` — **1 строка**,
  риск низкий (меняется только частота походов к сундуку, не что производится);
* цикл до 5 слотов за вызов `dumpOneMoreSlot` либо тикрейт `INVENTORY_FULL` 20 → 5 — **1-3 строки**,
  риск нулевой, касается **всех** профессий (прошлый круг оценил это как пункт 3 своего рейтинга).

## 2.2. Свободный режим делает любого копающего работника в 5.6 раза медленнее **[ИЗМЕРЕНО, обе стороны]**

**Что происходит.** `AbstractEntityAIBasic.holdEfficientTool` (`:1376`) в 26.2 имеет ветку, которой
**нет в 1.21.1**:

```java
if (worksWithoutTools())
{
    // No tool of the required kind and level is carried and none will be asked for, so mine bare handed
    // instead of refusing the block. …
    CitizenItemUtils.removeHeldItem(worker);
    return true;
}
requestTool(target, pos);
```

Дальше `calculateWorkerMiningDelay` (`AbstractEntityAIInteract.java:337`) делит на скорость инструмента
**в руке**:

```
задержка = 500 * 0.85^(уровень/2) * твёрдость / getDestroySpeed(инструмент, блок) * (1 - исследование)
```

С пустой рукой `getDestroySpeed` = 1.0. Для камня с алмазной киркой это 8.0. Отношение — **8×**.

**Измерено, обе стороны, на шахтёре в шахте (`mine5`, камень, свободный режим включён).** Считался
воздух в кубе 13×13×13 вокруг забоя:

```
голыми руками (как есть)      : 279 -> 287 = 8 блоков за 254 с  = 31.8 с/блок
после `give 5 diamond_pickaxe`: 288 -> 331 = 43 блока за 245 с  =  5.7 с/блок
```

**5.6×.** Отклонение от предсказанных 8× объясняется тем, что шахтёр между блоками ещё ходит и
закладывает кобблстоуном.

Тот же эффект на строителе, менее чисто (он и ломает, и ставит, поэтому счёт воздуха шумит):
**8 блоков за 305 с** до выдачи инструмента, **13 за 314 с** после; отдельным опросом поля
`blockToMine` — смена цели раз в **24 с** с киркой в инвентаре.

**Кого касается.** Всех, кто ломает блоки: шахтёр, строитель, карьерщик, лесоруб, фермер, нижний мир.
То есть в свободном режиме — почти вся колония.

**Апстрим или порт.** **Эта ветка.** В 1.21.1 `holdEfficientTool` (`:1334`) идёт сразу
`requestTool(target, pos); return false;` — ветки `worksWithoutTools()` там нет. Это добавление
free mode.

**Правка.** Не «не просить инструмент», а «выдать инструмент» — ровно как это уже сделано двумя
методами выше в том же файле: `checkForToolOrWeapon` (`:1000-1010`) и `checkForToolOrWeaponAsync`
(`:1048-1054`) в свободном режиме зовут `FreeMode.equip(...)`. В `holdEfficientTool` не хватает того же:

```java
if (worksWithoutTools())
{
    final EquipmentTypeEntry toolType = WorkerUtil.getBestToolForBlock(target, target.getDestroySpeed(world, pos), building, world, pos);
    FreeMode.equip(worker.getInventoryCitizen(), toolType, WorkerUtil.getCorrectHarvestLevelForBlock(target), building.getMaxEquipmentLevel());
    final int slot = getMostEfficientTool(target, pos);
    …  // если инструмент нашёлся — взять в руку, иначе прежнее поведение
}
```

**~6 строк**, две из них уже написаны в `requestTool` (`:1470-1473`) и просто переиспользуются.
**Риск низкий:** вне свободного режима ничего не меняется, внутри — работник получает предмет, который
free mode и так обязан ему дать. Комментарий на месте честно оговаривает, что не страдает выпадение
предметов, но про **скорость** там ничего нет — а стоит она в 5.6 раза.

## 2.3. Композтер не делает ничего, пока игрок не поставит галочку в GUI **[ИЗМЕРЕНО, обе стороны]**

**Что происходит.** `EntityAIWorkComposter.getMaterials` (`:148`) берёт
`building.getModuleMatching(ItemListModule.class, "compostables").getList()`, и если список пуст —
`complain(); return getState();`. Список создаётся однoаргументным конструктором
`new ItemListModule(COMPOSTABLE_LIST)` (`core/colony/buildings/modules/BuildingModules.java:81`), а он
оставляет `itemsAllowed = ImmutableList.of()` (`ItemListModule.java:34, :51-54`). Заполняется список
**только** галочками игрока в GUI хижины.

**Измерено, обе стороны.** Композтер с полностью построенной хижиной 5 уровня и **пятью
зарегистрированными бочками** просидел **100 % семплов (260 с) в `GET_MATERIALS` при 0 % движения**.
Дамп модулей в тот момент: `ItemListModule listId=compostables size=0`, `barrels=[5 позиций]`.
Одна команда `listadd -60 1 -60 compostables minecraft:wheat_seeds` (программный эквивалент галочки) —
и в течение нескольких секунд он ушёл в `COMPOSTER_FILL`, а за следующие 45 минут сделал 37 заливок и
регулярные сборы (§1).

**Что видит игрок.** Свежепостроенный композтер с работником стоит у хижины и не шевелится.
Сигнал есть, но слабый: `complain()` (`:405`) шлёт сообщение всем игрокам колонии не чаще раза в
`TICKS_UNTIL_COMPLAIN = 12000` вызовов ИИ. Это **поправка к §2.14 прошлого круга**, где было записано,
