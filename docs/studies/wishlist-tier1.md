## 1. Cinnabar → red dye

### 1.1 What cinnabar actually is in 26.2

Not an ore. Not a gem. **A decorative stone family**, like tuff:

```
Blocks.java:4908   CINNABAR = register(..., .sound(SoundType.CINNABAR).mapColor(COLOR_RED)
                                .requiresCorrectToolForDrops().strength(1.5F, 6.0F))
Blocks.java:4917-4928   CINNABAR_SLAB / STAIRS / WALL, POLISHED_CINNABAR (+slab/stairs/wall),
                        CINNABAR_BRICKS (+slab/stairs/wall), CHISELED_CINNABAR
Items.java:108-120      thirteen block items, no separate "raw cinnabar"
```
**[VERIFIED]**

It generates as noise bands in the new sulfur caves, alongside sulfur:

```
data/worldgen/SurfaceRuleData.java:82-86
    sulfurCaveBands = sequence(
        ifTrue(noiseCondition3d(Noises.SULFUR_CAVE_GRADIENT, -0.4F, -0.1F), CINNABAR),
        ifTrue(noiseCondition3d(Noises.SULFUR_CAVE_GRADIENT,  0.0,  0.4F), SULFUR),
        ifTrue(noiseCondition3d(Noises.SULFUR_CAVE_GRADIENT,  0.4F),        CINNABAR))
```
**[VERIFIED]**

Vanilla ships **34** cinnabar recipes, all of them stonecutting and crafting inside the family
(`chiseled_cinnabar.json`, `cinnabar_bricks_from_cinnabar_stonecutting.json`, …) and **no** recipe
that turns cinnabar into anything else. There is no vanilla cinnabar → dye path to teach. **[VERIFIED,
`unzip -l /opt/vanilla/server-26.2.jar 'data/minecraft/recipe/*cinnabar*'`]**

**This is the first thing worth telling him.** "Cinnabar to red dye" is real-world chemistry
(mercury sulfide is vermilion), but in 26.2 cinnabar is a *building block* you would be burning one
of for one dye. There is no nugget or shard version to consume instead. If he wanted this because he
assumed cinnabar was an ore that drops a red pebble, the feature does not read the way he imagines.

### 1.2 Is it really zero code?

Almost. The mod's own recipe formats are **generated by datagen providers, never hand-written**, so
"add a datapack entry" means "add a builder call and re-run `runDatagen`". Both providers already
exist; neither is new.

The dyer's custom recipe list is three entries long today:

```java
mc/core/generation/defaults/workers/DefaultDyerCraftingProvider.java:44-59
    recipe(DYER, MODULE_CRAFTING, "red_sand")     ...
    recipe(DYER, MODULE_CRAFTING, "black_dye")    ... .minBuildingLevel(2)
    recipe(DYER, MODULE_CRAFTING, "dark_prismarine") ... .minBuildingLevel(3)
```
producing `26.2/src/main/generated/data/minecolonies/crafterrecipes/dyer/{red_sand,black_dye,dark_prismarine}.json`.
**[VERIFIED]**

A fourth entry is six lines. The generated JSON is self-contained — inputs, result, optional
`min-building-level` — and needs **no matching vanilla recipe** to work:

```json
26.2/src/main/generated/data/minecolonies/crafterrecipes/dyer/black_dye.json
{ "type": "recipe", "crafter": "dyer_crafting",
  "inputs": [ { "id": "minecraft:charcoal" } ],
  "intermediate": "minecraft:air", "min-building-level": 2,
  "result": { "id": "minecraft:black_dye" } }
```
**[VERIFIED]**

**His "does an item need registering first?" question: no.** `ItemStorage` wraps any `ItemStack`;
custom recipes are loaded by `CrafterRecipeListener` and injected straight into the building by
`AbstractCraftingBuildingModule#checkForWorkerSpecificRecipes` (`mc/core/colony/buildings/modules/
AbstractCraftingBuildingModule.java:498-503`), which runs from `onColonyTick`
(same file, `:491-495`). Custom recipes **bypass the teach flow entirely** — they are not filtered by
`getIngredientValidator` or `isRecipeCompatible`, so the dyer's ingredient tags never get a vote.
**[VERIFIED]**

The "ordinary recipe" half — so a player can also craft it by hand — is five lines in
`mc/core/generation/defaults/DefaultRecipeProvider.java`, using the pattern already there at
`:498-502`:

```java
shapeless(RecipeCategory.MISC, Items.DYE.pick(DyeColor.RED))
        .requires(Items.CINNABAR)
        .unlockedBy("has_cinnabar", has(Items.CINNABAR))
        .save(consumer, key(Identifier.fromNamespaceAndPath(MOD_ID, "red_dye_from_cinnabar")));
```
**[VERIFIED as the existing pattern; the snippet itself is a proposal, not code in the tree]**

### 1.4 The traps

**His trap ("does an item need registering somewhere first") — does not exist.** Confirmed above.

Four he did not name:

1. **You would be spending a building block.** Covered in §1.1. Worth a decision, not a fix.

2. **The recipe id must be namespaced `minecolonies:`.** `RecipeBuilder#save` without an explicit key
   derives the id from the *output item*, which is `minecraft:red_dye` — that overwrites a vanilla
   recipe id. The existing calls at `DefaultRecipeProvider.java:502,509` pass
   `key(Identifier.fromNamespaceAndPath(MOD_ID, "doublefern"))` precisely for this reason.
   **[VERIFIED]**

3. **The custom entry and the ordinary recipe are partly redundant, and that is fine.** Adding the
   plain recipe alone already makes the dyer able to *learn* it: `red_dye` is in `#c:dyes`, which is
   the whole of `minecolonies:dyer_product`
   (`mc/core/generation/defaults/DefaultItemTagsProvider.java:363-364`, generated to
   `26.2/src/main/generated/data/minecolonies/tags/item/dyer_product.json`), and
   `isRecipeCompatibleBasedOnTags` decides on the *output* first
   (`mc/api/util/CraftingUtils.java:164-168`). The custom entry's only job is "known without being
   taught". Adding both is safe — `checkForWorkerSpecificRecipes` de-duplicates identical
   input/output pairs at `AbstractCraftingBuildingModule.java:513-560`. **[VERIFIED]**

4. **Do not add cinnabar to `minecolonies:dyer_ingredient` to "make it official".** The stonemason's
   excluded-ingredient tag swallows the entire dyer ingredient tag
   (`DefaultItemTagsProvider.java:540-544`), so anything put in there is taken away from the
   stonemason. **[VERIFIED]**

**Bonus, adjacent, cheaper than the feature itself:** the stonemason cannot work most of the cinnabar
family today, and it is not the mod's fault. The stonemason's ingredient list leans on
`ConventionalItemTags.STONES` (`DefaultItemTagsProvider.java:534`), and Fabric's
`fabric-convention-tags-v2 4.7.0` still ships `c:stones` as
`[stone, andesite, diorite, granite, tuff, deepslate]` — no cinnabar, no sulfur. **[VERIFIED by
unzipping the Fabric API jar]**

The damage is partial, which is what makes it odd in play. The stonemason *can* make the nine
cinnabar stairs, slabs and walls, because those items are in vanilla's `#minecraft:stairs`,
`#minecraft:slabs` and `#minecraft:walls` (three cinnabar entries in each **[VERIFIED]**) and the
stonemason product tag pulls all three in
(`26.2/src/main/generated/data/minecolonies/tags/item/stonemason_product.json:38-40`), and
`isRecipeCompatibleBasedOnTags` decides on the output first. But polished cinnabar, cinnabar bricks
and chiseled cinnabar are unreachable: they are in no stonemason product tag —
`#minecraft:stone_bricks` is only the four vanilla stone-brick items **[VERIFIED]** — and the plain
cinnabar block they are made from is in no stonemason ingredient tag either, so the check falls to
`.orElse(false)` (`mc/core/colony/buildings/workerbuildings/BuildingStonemason.java:73-76`).
A colonist who can cut cinnabar stairs but cannot cut cinnabar bricks is a strange thing to explain.
Two lines in the stonemason ingredient and product tags fix the whole family, sulfur included. If he
wants a genuine datapack-evening win in this area, that is a better one than the dye.

### 1.5 What it looks like in play

A dyer at any hut level starts turning cinnabar blocks into red dye without being taught, and the
courier starts pulling cinnabar out of the warehouse to feed him. Since cinnabar only shows up in
sulfur caves, in practice this is a mid-game red-dye source for a colony that has a miner working
deep, and a reason to keep cinnabar rather than use it as building stone. **[UNCHECKED — no client
here; this is read off the recipe and request paths, not observed.]**

## 2. A copper equipment tier

### 2.1 The short version

**The port already handles copper, correctly, and has since the tier table was written.** Neither
half of his fear is real: colonists do not treat copper as an unknown item, and there is no research
entry anywhere that keys off equipment material.

### 2.2 Why colonists already see copper

The equipment level table is not a hand-written list. It is built at startup by walking the entire
item registry:

```java
mc/api/equipment/ModEquipmentTypes.java:244-312   initRegisterEquipmentTiers()
    for (final Item item : BuiltInRegistries.ITEM) {
        final ToolMaterial material = toolMaterialOf(dummy);
        if (material != null)  Compatibility.registerItemTierIfAbsent(item, material, (int) material.attackDamageBonus());
        else if (dummy.get(DataComponents.EQUIPPABLE) != null) { ... ItemStackUtils.getArmorLevel(dummy) ... }
        ...
    }
```
called from `mc/core/MineColonies.java:215`. **[VERIFIED]**

And **copper is already in the material list it matches against**:

```java
mc/api/equipment/ModEquipmentTypes.java:317-320
    private static final ToolMaterial[] TOOL_MATERIALS = {
      ToolMaterial.WOOD, ToolMaterial.GOLD, ToolMaterial.STONE, ToolMaterial.COPPER,
      ToolMaterial.IRON, ToolMaterial.DIAMOND, ToolMaterial.NETHERITE };
```
**[VERIFIED]**

26.2 removed `TieredItem#getTier()`, so `toolMaterialOf` (`:334-351`) recovers the material by
matching durability. I checked that this is unambiguous across the *whole* item registry, not just
the seven materials:

```
DUR 32   -> [golden_sword, golden_shovel, golden_pickaxe, golden_axe, golden_hoe, golden_spear]
DUR 59   -> [wooden_*]
DUR 131  -> [stone_*]
DUR 190  -> [copper_sword, copper_shovel, copper_pickaxe, copper_axe, copper_hoe, copper_spear]
DUR 250  -> [iron_*, trident]
DUR 1561 -> [diamond_*]
DUR 2031 -> [netherite_*]
```
**[PROBE]** — and `toolMaterialOf` first requires membership of `#pickaxes/#axes/#shovels/#hoes/#swords`
(`:336-340`), which excludes the trident and the spears, so there is no collision at all.

Copper tools therefore score:

```
MAT COPPER dur=190 atkBonus=1.0 -> mcolLevel=1
MAT STONE  dur=131 atkBonus=1.0 -> mcolLevel=1
MAT IRON   dur=250 atkBonus=2.0 -> mcolLevel=2
```
**[PROBE]**

**Level 1, the same as stone — and that is the right answer, not a bug.** 26.2 has no copper mining
tier. `incorrect_for_copper_tool` and `incorrect_for_stone_tool` are byte-identical:

```json
both = { "values": [ "#minecraft:needs_diamond_tool", "#minecraft:needs_iron_tool" ] }
```
**[VERIFIED, from the 26.2 server jar]** — and there is no `needs_copper_tool` block tag at all
(`grep NEEDS_.*_TOOL /opt/mc-src/net/minecraft/tags/BlockTags.java` returns diamond, iron, stone
only). Copper is a *durability and speed* upgrade over stone, not a harvest-tier one. So
`WorkerUtil.getCorrectHarvestLevelForBlock` (`mc/core/util/WorkerUtil.java:206-228`), which maps
those three tags to 3/2/1, needs no new case, and the mining side of the feature is finished before
it starts.

Copper armour has no explicit entry in the mod's table, so it falls through the generic scan:

```java
mc/api/util/ItemStackUtils.java:101-124   VANILLA_ARMOR_DISTRIBUTION (leather/gold 1, chain 2, iron 3, diamond 4, netherite 5)
mc/api/util/ItemStackUtils.java:324-352   getArmorLevel(): unknown item -> compare (armor + 4*toughness)
                                          against the slot-ordered leather/chain/iron/diamond ladder
```
I replayed that arithmetic against the real items:

```
ARMOUR copper_helmet     armor=2.0 tough=0.0 value=2.0
ARMOUR copper_chestplate armor=4.0 tough=0.0 value=4.0
ARMOUR copper_leggings   armor=3.0 tough=0.0 value=3.0
ARMOUR copper_boots      armor=1.0 tough=0.0 value=1.0

COPPER-ARMOUR-LEVEL copper_helmet     -> mcol armour level 2
COPPER-ARMOUR-LEVEL copper_chestplate -> mcol armour level 2
COPPER-ARMOUR-LEVEL copper_leggings   -> mcol armour level 2
COPPER-ARMOUR-LEVEL copper_boots      -> mcol armour level 1
```
**[PROBE]**

So a guard already wears copper: helmet, chest and legs are graded as chainmail (level 2), boots as
leather/gold (level 1). Not "ignored as an unknown item" — the fallback ladder was written for
exactly this case.

### 2.3 Crafting and research

**Blacksmith teachability is already there and is material-agnostic.** The blacksmith's tags key off
ingots and nuggets, not on named tools:

```java
DefaultItemTagsProvider.java:272-284
    crafterIngredient(BLACKSMITH) .add(DIAMOND_BLOCK, EMERALD_BLOCK).addTags(NUGGETS, INGOTS)
    crafterProduct(BLACKSMITH)    .add(SHEARS, MACE).add(LIGHTNING_ROD…).addTags(NUGGETS, INGOTS)
```
`copper_ingot` is in `#c:ingots`, and `CraftingUtils.isRecipeCompatibleBasedOnTags` falls through the
(undecided) product check to the ingredient check (`mc/api/util/CraftingUtils.java:164-168`), exactly
as it does for iron tools today. Nothing in `crafterrecipes/blacksmith/` names a material tier — the
16 entries there are plate armour, netherite upgrades and the two assistant hammers. **[VERIFIED]**

**His research trap does not exist.** I read the whole combat branch of
`mc/core/generation/defaults/DefaultResearchProvider.java` (`:985-1120`). Every armour and tool
research there is a *durability or damage multiplier* — `ARMOR_DURABILITY`, `MELEE_ARMOR`,
`ARCHER_ARMOR`, `PLATE_ARMOR` — gated on a building level and paid for in iron ingots or diamonds.
The `Items.IRON_HELMET` / `Items.CHAINMAIL_CHESTPLATE` references in there are `setIcon(...)` calls
and item *costs*. Not one research entry anywhere reads an equipment level or a material.
**[VERIFIED]** The only "building-level requirement" that touches equipment is
`IBuilding#getMaxEquipmentLevel` (`mc/api/colony/buildings/IBuilding.java:479-490`), which is hut
level arithmetic and has no material in it — and it already accepts a level-1 copper tool at hut
level 1.

### 2.4 What is actually left

All of it is polish, and none of it is required:

1. **Two lang strings read wrong.** `26.2/src/main/resources/assets/minecolonies/lang/manual_en_us.json:1177`
   says `"com.minecolonies.coremod.toollevel.1": "Stone"`, and `:1171` says
   `"com.minecolonies.coremod.armorlevel.2": "Chain"`. These are what
   `ItemStackUtils.swapToolGrade/swapArmorGrade` (`mc/api/util/ItemStackUtils.java:432-456`) put in
   front of the player, so a request that copper satisfies still reads "Stone" or "Chain".
   `"Stone or Copper"` / `"Chain or Copper"` is the whole fix. **2 strings.** **[VERIFIED in the
   file; UNCHECKED that the GUI renders them — no client.]**

2. **Copper boots are graded one step below the rest of the set.** Level 1 versus 2 (§2.2). It means
   a Guard Tower in the chain band — `CHAIN_BUILDING_LEVEL_RANGE = (2,3)`,
   `mc/api/util/constant/GuardConstants.java:201` — will accept copper helmet, chest and legs but
   ask for something else on the feet. If that bothers him, four entries in
   `VANILLA_ARMOR_DISTRIBUTION` (`ItemStackUtils.java:101`) pin the whole set at 2. **~4 lines.**

3. **`Compatibility.LEVEL_TO_TIER` has no copper.**
   `{ WOOD, STONE, IRON, DIAMOND, NETHERITE, NETHERITE }` at
   `mc/api/compatibility/Compatibility.java:45-47`. Only used to hand a plausible `ToolMaterial` back
   to a third-party compat hook that registered by level number; it never affects colonist
   behaviour. **Cosmetic, 1 line, skippable.**

4. **`minecraft:copper_spear` scores level 0.** The spear type measures durability against the mod's
   own spear (`ModEquipmentTypes.java:176`, `durabilityBasedLevel` at `:229-237`), and 190/250 = 0 —
   the same bucket as wooden and stone spears. This is the pre-existing quirk the comment at
   `:169-174` already documents, not something copper introduced, and it is arguably right:
   a copper spear *is* worse than the mod's spear.

## 3. Animal variants by biome

### 3.1 Vanilla already does the entire feature

Both halves he described, verbatim, in vanilla 26.2:

```java
/opt/mc-src/.../animal/cow/Cow.java:72-78     getBreedOffspring: baby.setVariant(random.nextBoolean() ? this.getVariant() : partnerCow.getVariant())
/opt/mc-src/.../animal/cow/Cow.java:82-88     finalizeSpawn:     VariantUtils.selectVariantToSpawn(SpawnContext.create(level, blockPosition()), Registries.COW_VARIANT)
```
identically for pigs (`animal/pig/Pig.java:242-249, 311-317`) and chickens
(`animal/chicken/Chicken.java:175-182, 185-191`). **[VERIFIED]**

"Takes the biome's one by location" is pure data:

```json
data/minecraft/cow_variant/cold.json
{ "asset_id": "minecraft:entity/cow/cow_cold", "model": "cold",
  "spawn_conditions": [ { "condition": { "type": "minecraft:biome",
    "biomes": "#minecraft:spawns_cold_variant_farm_animals" }, "priority": 1 } ] }
```
plus `temperate.json` at priority 0 as the fallback and `warm.json` on
`#minecraft:spawns_warm_variant_farm_animals`. Nine files, three per animal, shipped by Mojang.
**[VERIFIED, from the 26.2 server jar]**

### 3.2 MineColonies is not in the way

This is the claim worth checking hardest, because "the change lands in the shepherd and cowhand AI"
presumes the mod is doing its own breeding. It is not.

**The herder never creates a baby.** All it does is set two adults in love and let vanilla's
`BreedGoal` take it from there:

```java
mc/core/entity/ai/workers/production/herders/AbstractEntityAIHerder.java:646-671   breedTwoAnimals()
    ...
    animal.setInLove(null);
    worker.swing(InteractionHand.MAIN_HAND);
    ...
```
That is the entire breeding implementation. `getBreedOffspring` is never called by mod code, never
overridden, never wrapped. **[VERIFIED]**

**The mod never spawns a cow, pig, sheep or chicken** except in one place, free mode's pen stocking:

```java
mc/core/entity/ai/animals/AnimalPen.java:327
    final Animal animal = types.get(...).spawn(level, spot, EntitySpawnReason.MOB_SUMMONED);
```
and `EntityType#spawn` routes through `create`, which calls `mob.finalizeSpawn(...)`
(`/opt/mc-src/net/minecraft/world/entity/EntityType.java:156-158, 178-212`, the `finalizeSpawn` at
`:204`). So even conjured animals get the biome's variant. **[VERIFIED]**

**No mod code reads or writes a variant.** `grep -rn "Variant" 26.2/src --include=*.java` returns
only Tinkers' slime *leaf* variants, `RackType`, and a tick-offset counter named
`tickOffsetVariant`. Nothing entity-related. **[VERIFIED]**

**The `AnimalManager` is a red herring for this feature.** Its own javadoc says so:
"The interface for managed animals, such as Cavalry horses. Note that this does not include farm
animals." (`mc/api/colony/managers/interfaces/IAnimalManager.java:20-22`). **[VERIFIED]**

**Sheep have no variant in 26.2** — `grep setVariant` over `animal/sheep/Sheep.java` finds nothing;
sheep still carry a `DyeColor` and vanilla still mixes parent colours in
`Sheep#getBreedOffspring:280`. So the shepherd, the one AI he named, has nothing to do with this at
all. **[VERIFIED]**

**Loot is variant-independent**, so nothing downstream cares: there is exactly one
`data/minecraft/loot_table/entities/cow.json`, one `pig.json`, one `chicken.json`. **[VERIFIED]**
That also means the one place the mod *does* build a variant-less dummy animal —
`RecipeAnalyzer.createAnimals` at `mc/core/colony/crafting/RecipeAnalyzer.java:125`, which uses
`entityType.create(level, MOB_SUMMONED)` and so skips `finalizeSpawn` and always gets temperate — is
harmless: it only feeds the JEI "what does a cowboy produce" preview, and the drops are the same
whichever variant it picked.

### 3.3 Size

Zero. No files, no lines, no lang keys, no datagen, and old saves are unaffected — animals already
in the world keep whatever variant they were given, since `VariantUtils.readVariant` restores it from
entity NBT (`Cow.java:66`).

### 3.4 The thing worth deciding instead

There *is* a real feature hiding here, and it is the one vanilla deliberately does **not** do.
Vanilla's rule is *inherit from a parent, always* — so a herd founded by two temperate cows stays
temperate forever, even in a desert colony, and the biome only ever matters for the wild animals
that wandered in. If what he actually wants is **"my colony's herd drifts to the local variant over
generations"**, that is a change *away* from vanilla and does need code.

The good news is that it needs neither a mixin nor an access widener, and I checked all three
obstacles:

* The hook exists and already special-cases animals:
  `ServerEntityEvents.ENTITY_LOAD` is registered at `mc/core/event/EventHandler.java:125`, and
  `onEntityAdded` already does `if (entity instanceof final Animal animal) AnimalPen.onAnimalLoaded(animal);`
  at `:183-186`. A newly bred baby fires it. **[VERIFIED]**
* The biome selection is public API: `VariantUtils.selectVariantToSpawn(SpawnContext.create(level, pos), Registries.COW_VARIANT)`
  — both `public static`, `/opt/mc-src/net/minecraft/world/entity/variant/VariantUtils.java:34-40`
  and `SpawnContext.java:10-13`. **[VERIFIED]**
